# Interview guide

## One-minute explanation

UnderScore takes one musical theme and produces the missing intensity layers for adaptive game music. A composer writes the theme once; the system generates the combat or boss layers while preserving the theme's key, tempo, chord progression and loop length. In the game, a deterministic conductor reads game state and schedules the transition one bar early. The runtime is not a model.

The research question is whether a small symbolic arranger can produce layers that listeners prefer to the industry-standard mute/filter baseline on held-out themes. The demo currently proves the runtime and loop contract with hand-authored layers; the trained arranger is the next phase.

## Why this is not "AI adaptive music"

Adaptive music already exists and works. The gap is not a model that reacts in real time. It is the labour of composing four synchronized versions of every cue. The model therefore belongs offline in content production, and its output is editable MIDI/audio. The runtime remains a scheduler.

## Architecture decisions and alternatives

| Decision | Why | Rejected alternative |
|---|---|---|
| Offline arranger | Musical reactions must be bar-quantized; a 200 ms model is too slow for a downbeat. | Model in the frame loop. |
| Deterministic conductor | Testable, explainable, sample-accurate, no network. | Learned scheduler. |
| Four complete mixes in the first demo | Simple synchronized crossfades; proves the stem contract. | Live per-note synthesis in v1. |
| One theme, four levels | Makes the production multiplier visible and the evaluation tractable. | Text-to-music from scratch. |
| Track-ablation labels | Gives real aligned layers from licensed multi-track data. | Hand-labelled intensity, which is subjective. |
| B1 mute/filter baseline | The honest non-ML competitor used by real teams. | Comparing only to silence or no music. |

## Why a trained model is necessary

A text prompt cannot guarantee that a layer follows a specific theme's bar grid, key, per-bar chords and loop point. The proposed model earns its place through hard constraints and local generation, not through a generic "AI soundtrack" claim. If B1 wins the listening test, the project will be reported as a benchmark or parked.

## Metrics

- Headline: blind 2AFC preference over B1, with CI.
- Chord-tone compliance ≥90%.
- Grid lock ≥95%.
- Loop-seam ratio <0.8.
- Intensity monotonicity ρ ≥0.8.
- Non-duplicate windows and motif recall together, not separately.
- Landing error in the runtime: zero by design.
- Generation time per 8 bars.

## What failed or is unresolved

- The current demo audio is generated by a small deterministic synth, not a trained model.
- The browser WAV decode initially failed because the metadata layer array was treated as an object; it is fixed.
- No Slakh ingestion, model, blind study or 70% preference result exists yet.
- The soundfont licence is unresolved.
- The target of 70% is a hypothesis, not a measured number.

## Likely questions

**Why not use a live model?**
Because game transitions are bar-quantized. The correct response is to schedule earlier, not generate faster.

**How do you know the layers are synchronized?**
All four stems share sample rate, tempo, bar count and exact duration. The browser starts them at one audio-clock timestamp and crossfades gains at the next bar.

**What is the ML contribution?**
A constrained symbolic arranger trained from track-ablation labels, evaluated on held-out themes and user preference against B1. The evaluation and constraints are the contribution, not a new transformer architecture.

**What would kill the project?**
If listeners do not prefer the generated layers over the mute/filter baseline, the ML is unjustified. The research plan makes that an explicit kill criterion.

**Why not Wwise/FMOD?**
They solve playback, not layer authoring. UnderScore should output stems that drop into them rather than replace them.
